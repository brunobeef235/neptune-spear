# ABABIL ARCHITECTURE

**Project:** Neptune Spear  
**System:** Ababil  
**Document Type:** System Architecture Specification  
**Status:** Initial Architecture Baseline  
**Version:** 1.0

---

## 1. PURPOSE

Ababil is the controlled security testing and experimental validation engine of Neptune Spear.

Its primary purpose is to validate security hypotheses generated by Argus through bounded, reproducible, and authorized experiments.

Ababil transforms static analysis hypotheses into test cases, executes approved tests within isolated environments, collects raw evidence, and returns structured results.

Ababil must never interpret the existence of a hypothesis as permission to execute a test.

## 2. CORE RESPONSIBILITIES

Ababil is responsible for:

1. Receiving structured hypotheses from Argus.
2. Validating target authorization and testing scope.
3. Evaluating execution risk and resource requirements.
4. Generating bounded test cases.
5. Preparing isolated testing environments.
6. Executing approved tests.
7. Enforcing time, memory, and resource limits.
8. Collecting raw execution evidence.
9. Classifying execution outcomes.
10. Returning structured results to the Neptune Spear ecosystem.

## 3. HIGH-LEVEL ARCHITECTURE

Ababil consists of the following logical components.

### 3.1 Hypothesis Intake

Receives hypotheses from Argus.

Each hypothesis should include:

- Unique identifier.
- Target project and code location.
- Security category.
- Supporting evidence.
- Preconditions.
- Input constraints.
- Expected behavior.
- Confidence level.
- Suggested test strategy.

Ababil must validate the schema and reject malformed or unsupported requests.

### 3.2 Scope and Authorization Validator

This component enforces the security boundaries of Ababil.

Responsibilities:

- Verify the approved target.
- Validate permitted files, modules, and services.
- Check authorization records.
- Enforce allowed testing operations.
- Reject targets outside the approved scope.
- Record authorization decisions.

Default behavior must be deny unless authorization is explicitly established.

Authorization must be specific to the target and operation, not inferred from a user's general intent.

### 3.3 Risk Assessment Engine

Evaluates the potential impact of a proposed experiment.

Factors include:

- Target sensitivity.
- Execution privileges.
- Potential destructive behavior.
- Network access.
- Filesystem access.
- Resource consumption.
- Execution duration.
- External side effects.

High-risk experiments must be rejected or require additional explicit approval according to the project's security policy.

### 3.4 Test Case Generator

Converts approved hypotheses into bounded test cases.

A test case should define:

- Test identifier.
- Parent hypothesis identifier.
- Target function or component.
- Input data.
- Preconditions.
- Execution method.
- Expected outcome.
- Maximum execution time.
- Maximum resource consumption.
- Cleanup requirements.
- Evidence collection requirements.

Generated test cases must remain within the authorization scope.

### 3.5 Sandbox Manager

Provides isolated environments for test execution.

The sandbox must enforce:

- Filesystem isolation.
- Process isolation.
- Network restrictions.
- Resource limits.
- Execution timeouts.
- Controlled input and output.
- Temporary workspace management.
- Cleanup after execution.

The sandbox must not rely solely on application-level checks for security isolation.

If the required isolation cannot be established, execution must not proceed.

### 3.6 Execution Engine

Runs approved test cases inside the sandbox.

Responsibilities:

- Validate execution configuration.
- Launch the approved test process.
- Monitor execution.
- Enforce resource limits.
- Capture standard output and standard error.
- Record exit status.
- Handle timeouts.
- Terminate processes when required.
- Preserve execution metadata.

The execution engine must not silently expand the approved test scope.

### 3.7 Evidence Collector

Collects raw evidence from each experiment.

Evidence may include:

- Standard output.
- Standard error.
- Exit code.
- Execution duration.
- Resource usage.
- Relevant logs.
- Input and output hashes.
- Reproduction metadata.
- Sandbox configuration.
- Termination reason.

Evidence must be traceable to its test case and parent hypothesis.

Raw evidence must remain distinguishable from conclusions derived from that evidence.

### 3.8 Result Analyzer

Classifies experiment outcomes.

Possible outcomes include:

- `CONFIRMED`
- `NOT_REPRODUCED`
- `INCONCLUSIVE`
- `BLOCKED`
- `REJECTED`
- `ERROR`
- `TIMEOUT`

A successful test execution does not automatically mean a vulnerability has been confirmed.

The result analyzer must distinguish technical execution success from security hypothesis validation.

### 3.9 Reporting and Handoff

Produces structured experiment reports for Argus and Thoth.

Reports should include:

- Hypothesis identifier.
- Test case identifier.
- Authorization decision.
- Execution environment.
- Test configuration.
- Raw evidence references.
- Observed behavior.
- Outcome classification.
- Confidence and limitations.
- Reproduction instructions within the approved scope.

## 4. EXECUTION PIPELINE

The intended execution pipeline is:

1. Receive hypothesis from Argus.
2. Validate hypothesis schema.
3. Validate authorization and target scope.
4. Assess experiment risk.
5. Generate bounded test cases.
6. Validate test cases.
7. Prepare isolated sandbox.
8. Verify sandbox restrictions.
9. Execute approved tests.
10. Collect raw evidence.
11. Analyze execution results.
12. Generate structured report.
13. Return results to Argus and Thoth.
14. Clean up temporary resources.

Every stage must produce traceable status information.

## 5. SECURITY AND EXECUTION BOUNDARIES

Ababil must follow strict security principles.

### 5.1 Authorization First

No experiment may execute without explicit authorization for the target and operation.

### 5.2 Isolation by Default

Testing must occur in an isolated environment or an explicitly approved replica.

### 5.3 Least Privilege

Test processes must receive only the minimum permissions required.

### 5.4 Bounded Execution

Every experiment must have defined resource and time limits.

### 5.5 No Uncontrolled External Effects

Unapproved network access, external service interaction, destructive filesystem operations, and production modifications are prohibited.

### 5.6 Fail Closed

If authorization, sandbox integrity, or execution constraints cannot be verified, Ababil must refuse execution.

## 6. INTERACTION WITH OTHER SYSTEMS

### 6.1 Argus

Argus provides security hypotheses and supporting static analysis evidence.

Ababil validates those hypotheses experimentally and returns observed results.

Ababil must not modify Argus analysis conclusions directly.

### 6.2 Thoth

Thoth independently audits:

- Hypothesis quality.
- Authorization decisions.
- Test case validity.
- Sandbox compliance.
- Raw evidence.
- Outcome classification.
- Unsupported conclusions.

Ababil must preserve sufficient evidence for independent review.

### 6.3 Shared Core

Ababil uses Shared Core for:

- Common data models.
- Hypothesis schemas.
- Test case schemas.
- Evidence formats.
- Configuration.
- Logging.
- Serialization.
- Inter-system communication.

Ababil must maintain compatibility with approved Shared Core contracts.

## 7. RESOURCE MANAGEMENT

The initial target environment is:

- Operating System: Windows 11.
- Python: 3.13.
- Memory: 8 GB RAM.
- CPU: Intel Core i5-8365U.
- GPU: Intel UHD Graphics 620.

Ababil must use conservative resource limits.

The system should support:

- Maximum concurrent executions.
- Per-test memory limits.
- Per-test execution timeouts.
- Maximum output size.
- Temporary storage limits.
- Automatic cleanup.

Sandbox capabilities must be validated on the actual target operating system.

A sandbox implementation must not be considered secure merely because it runs in a separate process.

## 8. CURRENT IMPLEMENTATION BASELINE

Ababil is currently an architectural design target.

The existence of this document does not imply that sandbox management, authorization enforcement, test generation, or secure execution has already been implemented.

All capabilities must be implemented and independently validated before being considered operational.

## 9. KNOWN LIMITATIONS AND FUTURE WORK

Planned capabilities include:

- Authorization policy engine.
- Test case schema and validator.
- Sandbox abstraction layer.
- Windows-compatible isolation strategy.
- Execution supervisor.
- Resource monitoring.
- Evidence storage.
- Reproducible experiment records.
- Automated cleanup.
- Integration with Argus.
- Independent audit interface for Thoth.

Security-critical components require dedicated testing and review.

## 10. DEFINITION OF DONE

An Ababil capability is considered complete only when:

1. Its technical specification is approved.
2. Its implementation is integrated.
3. Relevant automated tests exist.
4. Tests have actually been executed.
5. Authorization boundaries are validated.
6. Isolation assumptions are documented and tested.
7. Resource limits are enforced.
8. Evidence is reproducible and traceable.
9. Failure behavior is tested.
10. Thoth can independently audit its outputs.
11. The Project Director approves completion.

Implementation alone does not mean a capability is complete.

## 11. ARCHITECTURE GOVERNANCE

This document defines the initial architectural baseline for Ababil.

Major changes to authorization, sandboxing, execution privileges, resource boundaries, evidence formats, and inter-system interfaces require a documented proposal and approval from the Project Director.

All implementation tasks must follow the approved architecture and NSDP workflow.
