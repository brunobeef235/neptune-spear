# THOTH ARCHITECTURE

**Project:** Neptune Spear  
**System:** Thoth  
**Document Type:** System Architecture Specification  
**Status:** Initial Architecture Baseline  
**Version:** 1.0

---

## 1. PURPOSE

Thoth is the independent auditing, verification, and quality assurance engine of Neptune Spear.

Its primary purpose is to independently evaluate the findings generated by Argus and the experimental evidence collected by Ababil.

Thoth must determine whether conclusions are supported by sufficient evidence, whether analysis assumptions are justified, and whether experimental results are correctly interpreted.

Thoth is not merely a report formatter. It is an independent reasoning and verification system.

## 2. CORE RESPONSIBILITIES

Thoth is responsible for:

1. Auditing Argus static analysis findings.
2. Verifying the logical consistency of analysis conclusions.
3. Reviewing Ababil test cases and execution evidence.
4. Identifying false positives.
5. Identifying potential false negatives and analysis gaps.
6. Detecting unsupported assumptions.
7. Evaluating evidence quality and completeness.
8. Checking consistency between hypotheses and experimental outcomes.
9. Producing independent audit reports.
10. Recommending improvements to Argus, Ababil, and Shared Core.

Thoth must distinguish verified facts, reasonable inferences, uncertain conclusions, and unsupported claims.

## 3. INDEPENDENCE PRINCIPLE

Thoth must evaluate evidence independently rather than automatically accepting conclusions from Argus or Ababil.

It must not assume that:

- Every Argus finding is a real vulnerability.
- Every Ababil test result is valid.
- A successful test execution confirms a vulnerability.
- An unsuccessful test proves that a vulnerability does not exist.
- High confidence from another system guarantees correctness.

Thoth should be able to disagree with both systems when the evidence supports a different conclusion.

## 4. HIGH-LEVEL ARCHITECTURE

Thoth consists of the following logical components.

### 4.1 Audit Intake Layer

Receives analysis findings, experiment reports, and evidence references.

Supported inputs include:

- Argus analysis reports.
- Argus security hypotheses.
- IR and graph references.
- Ababil test case definitions.
- Ababil execution records.
- Raw evidence references.
- Shared Core metadata.

Every input must be validated before auditing.

### 4.2 Evidence Validation Engine

Evaluates whether supplied evidence is complete, consistent, and traceable.

Checks include:

- Evidence identifiers.
- Source locations.
- Parent hypothesis relationships.
- Test case relationships.
- Execution metadata.
- Evidence integrity metadata.
- Missing or contradictory records.

Evidence must not be treated as reliable merely because another system produced it.

### 4.3 Argus Audit Engine

Independently evaluates Argus findings.

Responsibilities:

- Check whether findings follow from source code evidence.
- Review source and sink identification.
- Evaluate taint propagation assumptions.
- Inspect control-flow and data-flow reasoning.
- Identify missing validation or sanitization logic.
- Detect unreachable or unsupported execution paths.
- Identify possible false positives.
- Identify possible missed cases.

Where possible, Thoth should use independent verification methods rather than simply repeating Argus analysis.

### 4.4 Ababil Audit Engine

Reviews experimental testing and execution evidence.

Responsibilities:

- Verify that the test corresponds to its parent hypothesis.
- Check authorization records.
- Review sandbox configuration and execution constraints.
- Inspect test inputs and observed outputs.
- Check timeout and termination records.
- Evaluate whether the result classification is justified.
- Identify incomplete or misleading evidence.
- Detect inconsistencies between reported and observed behavior.

Thoth must not assume that a test was safely isolated merely because Ababil reports that it was.

### 4.5 Logical Consistency Engine

Evaluates the internal consistency of findings and reports.

Potential techniques:

- Rule-based verification.
- Boolean logic.
- Constraint checking.
- Graph consistency analysis.
- Dependency validation.
- Contradiction detection.
- Cross-report comparison.

The engine should identify conclusions that conflict with their own evidence or assumptions.

### 4.6 False Positive Analysis

Evaluates whether a reported finding may not represent an actual vulnerability.

Potential causes include:

- Incorrect source identification.
- Incorrect sink identification.
- Missing sanitization recognition.
- Unreachable code paths.
- Invalid assumptions.
- Incorrect data-flow relationships.
- Misinterpreted experimental evidence.

A suspected false positive must include the reasoning and evidence behind that assessment.

### 4.7 False Negative and Coverage Analysis

Evaluates potential gaps in the analysis.

Potential areas include:

- Unanalyzed functions.
- Unsupported language constructs.
- Missing call relationships.
- Incomplete data-flow coverage.
- Unresolved aliases.
- Unexamined execution paths.
- Missing test cases.
- Incomplete evidence collection.

Thoth must distinguish a confirmed missed vulnerability from a potential analysis gap.

### 4.8 Audit Report Generator

Produces structured and human-readable audit reports.

Reports should include:

- Audit identifier.
- Audited system and version.
- Input references.
- Evidence reviewed.
- Verification methods.
- Confirmed inconsistencies.
- Suspected false positives.
- Potential false negatives.
- Confidence and limitations.
- Recommendations.
- Final audit disposition.

### 4.9 Feedback and Improvement Engine

Generates recommendations for improving Neptune Spear.

Recommendations may concern:

- Argus parsing and analysis.
- IR design.
- CFG and Call Graph accuracy.
- Taint analysis.
- Ababil test generation.
- Sandbox enforcement.
- Evidence collection.
- Shared Core schemas.
- Test coverage.
- Documentation and governance.

Recommendations must be traceable to audit findings.

Thoth must not automatically modify production code or architecture.

## 5. AUDIT PIPELINE

The intended audit pipeline is:

1. Receive audit request.
2. Validate input schemas.
3. Identify relevant evidence.
4. Verify evidence traceability.
5. Audit Argus conclusions.
6. Audit Ababil test definitions and results.
7. Evaluate logical consistency.
8. Identify false-positive candidates.
9. Identify potential analysis gaps.
10. Assign audit conclusions and confidence.
11. Generate audit report.
12. Deliver recommendations.
13. Preserve audit records for future review.

Audits should support partial evaluation when some evidence is unavailable.

Missing evidence must be explicitly reported.

## 6. AUDIT OUTCOME CLASSIFICATION

Thoth should support the following audit dispositions:

- `SUPPORTED`: The conclusion is adequately supported by reviewed evidence.
- `SUPPORTED_WITH_LIMITATIONS`: The conclusion is supported, but important limitations remain.
- `INCONSISTENT`: The conclusion conflicts with available evidence.
- `INSUFFICIENT_EVIDENCE`: The available evidence cannot justify a conclusion.
- `POTENTIAL_FALSE_POSITIVE`: A finding may not represent a real vulnerability.
- `POTENTIAL_FALSE_NEGATIVE`: A possible missed issue or analysis gap has been identified.
- `REQUIRES_REVIEW`: Human review is required.

These dispositions describe audit status and must not be confused with vulnerability severity.

## 7. CONFIDENCE AND UNCERTAINTY

Thoth must communicate uncertainty explicitly.

Confidence should consider:

- Evidence quality.
- Evidence completeness.
- Reproducibility.
- Independent verification.
- Assumption validity.
- Contradictory evidence.
- Unsupported language features.
- Analysis coverage.

Confidence must not be calculated solely by averaging confidence values from Argus and Ababil.

Where numerical confidence is used, its methodology must be documented and validated.

## 8. INTERACTION WITH OTHER SYSTEMS

### 8.1 Argus

Thoth receives findings, hypotheses, and supporting analysis evidence from Argus.

It evaluates whether conclusions are justified and provides feedback on weaknesses.

Thoth must not silently rewrite Argus findings.

### 8.2 Ababil

Thoth receives test definitions, execution metadata, and raw evidence from Ababil.

It independently evaluates whether experimental conclusions are justified.

Thoth must not bypass Ababil's authorization or sandbox boundaries.

### 8.3 Shared Core

Thoth uses Shared Core for:

- Common data models.
- Evidence schemas.
- Finding schemas.
- Audit records.
- Configuration.
- Logging.
- Serialization.
- Inter-system communication.

Thoth must preserve references to original evidence and avoid altering raw evidence.

## 9. RESOURCE CONSTRAINTS

The initial target environment is:

- Operating System: Windows 11.
- Python: 3.13.
- Memory: 8 GB RAM.
- CPU: Intel Core i5-8365U.
- GPU: Intel UHD Graphics 620.

Thoth must prioritize efficient verification techniques.

Large audit workloads should support incremental processing and bounded memory consumption.

Independent verification must remain practical on the target hardware.

## 10. CURRENT IMPLEMENTATION BASELINE

Thoth is currently an architectural design target.

The existence of this document does not imply that independent auditing, false-positive analysis, false-negative analysis, or evidence verification has already been implemented.

Each capability must be implemented, tested, and independently evaluated before being considered operational.

## 11. KNOWN LIMITATIONS AND FUTURE WORK

Planned capabilities include:

- Evidence integrity verification.
- Independent finding validation.
- Cross-system consistency checks.
- False-positive analysis.
- Analysis coverage assessment.
- Logical contradiction detection.
- Audit confidence methodology.
- Reproducible audit records.
- Feedback generation.
- Integration with Argus and Ababil.

The quality of Thoth depends on the quality and completeness of the evidence it receives.

## 12. DEFINITION OF DONE

A Thoth capability is considered complete only when:

1. Its technical specification is approved.
2. Its implementation is integrated.
3. Relevant automated tests exist.
4. Tests have actually been executed.
5. Verification logic is documented.
6. Evidence traceability is demonstrated.
7. Known limitations are documented.
8. Audit results are reproducible.
9. Independence from the audited conclusion is demonstrated.
10. The Project Director approves completion.

Implementation alone does not mean a capability is complete.

## 13. ARCHITECTURE GOVERNANCE

This document defines the initial architectural baseline for Thoth.

Major changes to audit independence, evidence validation, outcome classification, confidence methodology, and inter-system interfaces require a documented proposal and approval from the Project Director.

All implementation tasks must follow the approved architecture and NSDP workflow.
