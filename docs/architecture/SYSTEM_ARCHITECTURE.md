## 1. PURPOSE

This document defines the high-level system architecture of Neptune Spear.

It establishes the responsibilities, boundaries, interactions, and shared principles of the three primary systems:

1. Argus
2. Ababil
3. Thoth

This document serves as the primary architectural reference for all development agents.

Detailed implementation specifications must remain consistent with this document.

## 2. SYSTEM OVERVIEW

Neptune Spear is a local-first intelligent code analysis and authorized security testing system.

Its primary objectives are:

- Understand program structure and behavior.
- Identify potential security weaknesses.
- Generate testable hypotheses.
- Validate hypotheses through controlled experiments.
- Independently audit findings and evidence.
- Produce understandable and reproducible reports.

The system consists of three primary subsystems and a shared foundation.

## 3. CORE COMPONENTS

### 3.1 ARGUS — Analysis Engine

Argus is responsible for static code analysis and program understanding.

Primary responsibilities:

- Source code parsing.
- Intermediate representation generation.
- Control-flow analysis.
- Data-flow and dependency analysis.
- Semantic and structural analysis.
- Vulnerability hypothesis generation.
- Evidence collection.
- Analysis result reporting.

Argus produces structured findings and candidate hypotheses for further validation.

Argus must distinguish confirmed facts from assumptions and unverified hypotheses.

### 3.2 ABABIL — Experimentation Engine

Ababil is responsible for controlled validation of hypotheses generated by Argus.

Primary responsibilities:

- Receive structured hypotheses.
- Generate bounded mathematical test cases.
- Prepare authorized test inputs.
- Execute experiments in isolated environments.
- Capture runtime behavior.
- Preserve raw evidence.
- Return experiment results.

Ababil must operate only within explicitly authorized environments.

### 3.3 THOTH — Independent Audit Engine

Thoth independently evaluates the outputs of Argus and Ababil.

Primary responsibilities:

- Review analysis findings.
- Examine experimental evidence.
- Detect unsupported conclusions.
- Identify missed cases.
- Evaluate consistency and reproducibility.
- Generate independent audit reports.
- Recommend improvements to other systems.

Thoth must not blindly trust the conclusions of Argus or Ababil.

## 4. SHARED FOUNDATION

The three systems use a shared foundation to maintain consistency.

The shared foundation is expected to provide:

- Common data models.
- Opcode and instruction registries.
- Communication schemas.
- Evidence formats.
- Versioning mechanisms.
- Configuration management.
- Logging and error handling.
- Shared validation utilities.

The exact modules and interfaces will be defined in a separate Shared Core specification.

## 5. HIGH-LEVEL DATA FLOW

The intended workflow is:

1. Source code is submitted to Argus.
2. Argus analyzes the code and produces findings.
3. Candidate hypotheses are transferred to Ababil.
4. Ababil conducts authorized controlled experiments.
5. Raw experimental evidence is returned.
6. Thoth independently audits the analysis and evidence.
7. Reports are generated for human review.
8. Approved feedback may be used to improve future analysis.

No automated feedback loop may silently modify critical architecture or security boundaries.

## 6. TRUST AND RESPONSIBILITY BOUNDARIES

Each subsystem has a distinct responsibility.

| System | Primary responsibility | Must not |
|---|---|---|
| Argus | Static analysis | Claim runtime exploitability without evidence |
| Ababil | Controlled experiments | Test unauthorized targets |
| Thoth | Independent audit | Blindly approve other systems |
| Project Director | Final governance | Delegate final authority to AI |

Subsystems must communicate through documented and versioned interfaces.

## 7. LOCAL-FIRST DESIGN PRINCIPLES

Neptune Spear prioritizes local execution.

Architectural requirements:

- Core functionality must not require hosted LLM services.
- Cloud inference must not be mandatory.
- Hardware resource consumption must be measured.
- Components should support modular development.
- External dependencies must be justified.
- Graceful degradation should be considered for constrained hardware.

## 8. SECURITY PRINCIPLES

The architecture must enforce:

- Explicit authorization boundaries.
- Isolated experiment environments.
- Input and resource limits.
- Evidence integrity.
- Clear separation of analysis and execution.
- Human approval for critical changes.
- Reproducibility and auditability.
